# Gate the sinks, then sanitize the stream

ctx-guard should treat prompt injection mainly as a problem of controlling actions. Detecting injected text is the weaker half. The control with real evidence behind it is deterministic: once a session has read untrusted content, ctx-guard gates the few actions every real coding-agent exploit has ended in. Those are writes to agent config, reading secrets and then sending data out, and destructive commands. The gate is a "tainted session" policy enforced in PreToolUse. Beneath it sits a cheap, stdlib-only sanitizer that runs next to the existing `redact_file` step in `ctx-guard-run` and in the PostToolUse hook `context_monitor.py`. The sanitizer strips invisible Unicode, neutralizes fake conversation and harness markers, flags markdown that would exfiltrate data, and annotates rather than blocks. The split follows the evidence. Adaptive attackers broke all 12 published injection defenses they tested, most at over 90% success ([Nasr et al.](https://arxiv.org/abs/2510.09023v1)). Tool-output false-positive rates for published detectors range from 0% to over 90% ([arXiv 2610.03448](https://arxiv.org/abs/2610.03448)). Deterministic command restriction is one of the few mechanisms with a good security/utility tradeoff in a six-harness study ([HarnessSecurity-Bench](https://arxiv.org/abs/2610.07639)). The hook surface now allows more than ctx-guard's docs say. Claude Code (v2.1.121+) and Copilot CLI can replace any tool's output before the model sees it, so built-in Read, Grep, WebFetch and MCP output can be sanitized as well as annotated. Codex CLI can only replace the whole result. Antigravity CLI's PostToolUse receives no tool output, so there ctx-guard can only defend before execution or inside its own wrapper. The honest claim for ctx-guard is "raises attacker cost and blocks specific dangerous follow-on actions", never "prevents prompt injection".

## Detection catches the opportunist, never the adaptive attacker

The literature agrees on the ceiling. OWASP's cheat sheet states that input screening "is not a security boundary". It also says keyword filters both false-positive and miss paraphrased, multilingual or encoded injections, and that guardrail models are themselves injectable ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)). "The Attacker Moves Second" bypassed **every detector evaluated, even when multiple guardrails were combined**, yet still calls detectors "a useful—but limited—component" against unsophisticated attacks ([arXiv 2510.09023](https://arxiv.org/abs/2510.09023v1)). Machine-learning classifiers fare no better under pressure. Spacing out characters dropped Prompt-Guard-86M's detection to 0.2% ([Robust Intelligence](https://www.robustintelligence.com/blog-posts/bypassing-metas-llama-classifier-a-simple-jailbreak)). Character injection evaded Azure Prompt Shield and Prompt Guard "in some instances up to 100%" ([arXiv 2504.11168](https://arxiv.org/abs/2504.11168)). Because ctx-guard is open source, every attacker can read its rules, so the realistic adversary is the adaptive one.

Classifiers also over-flag exactly the vocabulary developers use. On 339 benign sentences containing trigger words such as "ignore" and "cancel", PromptGuard v1 scored **0.88% accuracy** and ProtectAI v2 scored 56.64% ([InjecGuard](https://arxiv.org/html/2410.22770v3)). Perplexity filters false-positive on "code, url, math", which describes most of a developer's output ([Gemini defense paper](https://arxiv.org/pdf/2505.14534)). Known-answer detection (DataSentinel) and Attention Tracker need a local LLM or access to the model's internals. ctx-guard has neither, because the agent's model runs remotely, and secret-knowledge detectors were among those Nasr et al. defeated ([arXiv 2504.11358](https://arxiv.org/pdf/2504.11358); [arXiv 2411.00348](https://arxiv.org/abs/2411.00348)).

Within those limits, the detection techniques that fit ctx-guard's stdlib, offline, low-latency constraints rank clearly by value per false positive:

| Rank | Technique | Precision on dev output | Action | Feasibility |
|---|---|---|---|---|
| 1 | Invisible Unicode: Tag block U+E0000–E007F, bidi overrides, U+2061–2064, private-use and unassigned code points | Very high | Strip and count; decode tag text into a warning | `unicodedata`, one O(n) pass |
| 2 | Context-escape markers: fake harness tags (`</tool_result>`, `<system-reminder>`), line-initial `Human:`/`Assistant:`, chat-template tokens | High outside LLM codebases | Escape and annotate | `re` |
| 3 | Exfiltration-shaped markup: markdown images or links with data in the query string, `<img src>`, Mermaid image URLs | High | Defang the URL and annotate | `re` |
| 4 | Tightened "ignore previous instructions" grammar (Rebuff/Vigil family) | Low to medium | Annotate only, and require co-occurring signals | `re` or `difflib` |
| 5 | Llama Prompt Guard 2 (22M/86M) | Better than older classifiers, still evadable | Optional external command, annotate | Needs torch or ONNX; off by default |

Invisible Unicode comes first because attackers already use it and legitimate developer text almost never contains it. Unicode Tag characters mirror ASCII invisibly, and LLMs read them; Rehberger used them to smuggle prompts into Microsoft Copilot ([Embrace The Red](https://embracethered.com/blog/posts/2024/hiding-and-finding-text-with-unicode-tags/)). Blocking only the Tag block is insufficient. "Sneaky Bits" encodes text in binary using U+2062/U+2064, and ASCII Smuggler supports variation selectors ([Embrace The Red](https://embracethered.com/blog/posts/2025/sneaky-bits-and-ascii-smuggler)). GitHub now tries to "remove any invisible or masked information via Unicode or HTML tags" before its agents read issues ([GitHub blog](https://github.blog/security/how-githubs-agentic-security-principles-make-our-ai-agents-as-secure-as-possible/)). Characters with legitimate uses need a gentler tier: zero-width joiners in emoji, a BOM at file start, Indic and Arabic shaping. Flag them only in long runs or outside emoji context. OWASP's caveat applies to all of this: **NFKC does not remove zero-width characters or map homoglyphs**, so normalization has to be explicit ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)).

The phrase grammar is the weakest layer, and the most tempting to over-trust. Rebuff's heuristic expands to 8,800 verb × adjective × object phrases. Its object list includes "data", "input" and "response", and it defines no threshold ([Rebuff](https://raw.githubusercontent.com/protectai/rebuff/main/python-sdk/rebuff/detect_pi_heuristics.py)). Vigil's YARA rule is the same grammar ([Vigil](https://raw.githubusercontent.com/deadbits/vigil-llm/main/data/yara/instruction_bypass.yar)). On shell output, "skip tests", "ignored 3 files" and `git diff --ignore-all-space` would trip it constantly. ctx-guard should require a qualifier (previous/prior/above) *and* an instruction noun (instructions/rules/prompt), plus a second signal such as a second-person address to "you", "the assistant" or "AI". Encoded payloads are worth decoding only on candidate runs under a size cap, and only reported when the decoded text is printable and itself matches a signature. Otherwise lockfile hashes and JWTs become noise. Every surveyed open-source hook guard (Lasso, injection-sentinel, parry) warns instead of blocking on output scans for this reason ([lasso-security/claude-hooks](https://github.com/lasso-security/claude-hooks); [injection-sentinel](https://github.com/CodeCombustion/injection-sentinel); [parry](https://github.com/vaporif/parry)).

## Deterministic sink control is the only layer with a security story

The defenses with real guarantees all change *what can happen after* untrusted data enters context, not whether it gets noticed. CaMeL extracts control flow from the trusted query so untrusted data "can never impact the program flow". It solves 77% of AgentDojo tasks with provable security, against 84% undefended ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)). Microsoft's FIDES labels content as trusted or untrusted and as public or private, then blocks sensitive tool calls while untrusted content is in scope. With policy checks on, it stops all AgentDojo injection attacks ([MSR](https://www.microsoft.com/en-us/research/publication/securing-ai-agents-with-information-flow-control/)). The shipped version blocks a worked example in which an injected issue leads the agent to read `.env` and then call `post_comment` ([Agent Framework blog](https://devblogs.microsoft.com/agent-framework/fides/)). Willison's lethal trifecta has three legs: private data, untrusted content and external communication. Meta's Rule of Two covers untrusted input, sensitive access and state change. Both reach the same rule: when all three are present, the agent needs a human or a deterministic check ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/); [Meta](https://ai.meta.com/blog/practical-ai-agent-security/)).

ctx-guard cannot build CaMeL. It has no model, and it cannot follow a value into the model's reasoning. It can, however, approximate FIDES at whole-session granularity, which matches FIDES's own behavior when untrusted content is not auto-hidden. A coding agent on a developer machine always holds private data, so ctx-guard works on the other two legs: it marks when untrusted content enters, and it gates communication and consequential actions afterwards. The sinks to gate come straight from incident history. Copilot CVE-2025-53773 made the agent write `"chat.tools.autoApprove": true` into its own settings ([Embrace The Red](https://embracethered.com/blog/posts/2025/github-copilot-remote-code-execution-via-prompt-injection/)). In the GitHub MCP "toxic agent flow", a malicious public issue led the agent to leak private repositories through a public PR ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). The Amazon Q extension shipped a prompt instructing the agent to delete local files and cloud resources ([The Register](https://www.theregister.com/2025/07/24/amazon_q_ai_prompt/)). In "Comment and Control", PR titles and HTML comments leaked API keys from three CI-integrated agents ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-github-action-prompt-injection/)). **Every one of these ends in a config write, secret exfiltration or destruction**, and a command-level gate can recognize all three. HarnessSecurity-Bench supports the approach: command allowlisting cut attacks with small utility loss, and denylisting cut attacks *and* improved utility. Network isolation and read-only mode cost "substantial" utility ([arXiv 2610.07639](https://arxiv.org/abs/2610.07639)).

Spotlighting is the other structural idea, and it deserves a narrow role. Hines et al. cut ASR from over 50% to under 2% with datamarking or encoding, while plain delimiters only halved it ([arXiv 2403.14720](https://arxiv.org/abs/2403.14720)). Those results are on 2023 GPT models with non-adaptive attacks, and DeepMind reports that spotlighting lost much of its effect against adaptive attackers ([DeepMind](https://deepmind.google/blog/advancing-geminis-security-safeguards/)). Datamarking (replacing whitespace) would corrupt the code and paths an agent must copy exactly. Base64 encoding would break ctx-guard's compression and recall. What survives is a **per-invocation random-nonce envelope** around wrapped output, following the paper's own randomization advice, with any literal envelope prefix inside the body escaped. The envelope has a structural weakness: its framing reaches the model as tool output, with no more authority than the attacker's text. A trailing "data, not instructions" reminder shares that weakness. Learn Prompting documents dictionary attacks against the sandwich defense, and Hines et al. measured instructions alone as having "a very modest effect" ([Learn Prompting](https://learnprompting.org/docs/prompt_hacking/defensive_measures/sandwich_defense)). Both are a few tokens of hygiene, nothing more.

Context minimization is the most underrated lever, and ctx-guard already has most of it. `ctx-guard-run` decides what text the model sees and archives the rest for `ctx-guard-recall`. For high-risk carriers such as issue and PR bodies, `curl` bodies and READMEs of freshly cloned repos, it can show structural facts by default (exit code, counts, paths, matched error lines) and require an explicit recall for free-form third-party prose. That is a deterministic, stdlib version of the design-patterns paper's "strict data formatting" option for coding agents ([arXiv 2506.08837](https://arxiv.org/html/2506.08837)). Claude Code ships the LLM version of the same idea, where WebFetch returns a separate model's answer instead of the raw page ([Claude Code security](https://code.claude.com/docs/en/security)).

## Four agents expose four very different hook surfaces

Where the defense can act depends entirely on the host. The capability gap between agents is larger than the gap between detection techniques.

| Agent | Replace output | Warn after output | Pre-gate "ask" | Pre-gate "deny" | ctx-guard wiring today |
|---|---|---|---|---|---|
| Claude Code | Yes: `updatedToolOutput`, all tools, v2.1.121+ | `additionalContext`, `decision:block` | Yes | Yes | PreToolUse Bash, Read\|Grep; PostToolUse `*`; UserPromptSubmit |
| Copilot CLI | Yes: `modifiedResult` | `additionalContext` (≤10 KB) | Yes, but denied in autopilot | Yes | PreToolUse Bash, Read\|Grep; PostToolUse `*` |
| Codex CLI | Whole result only, via `decision:block` | `additionalContext` | No ("parsed but not supported") | Yes | PreToolUse `^Bash$` only |
| Antigravity CLI | No (PostToolUse gets no output) | No | Yes, plus `force_ask` | Yes, plus `deny_unless_prior_grant` | PreToolUse `run_command` only |

Sources: [Claude Code hooks](https://code.claude.com/docs/en/hooks#posttooluse-decision-control), [Copilot hooks](https://docs.github.com/en/copilot/reference/hooks-configuration), [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Antigravity hooks](https://antigravity.google/docs/hooks/), and ctx-guard's own [install.sh](../install.sh) and [agent_hooks.py](../hooks/lib/agent_hooks.py).

The biggest change is on Claude Code. Its PostToolUse `updatedToolOutput` "replaces the tool's output with the provided value before it is sent to Claude", for every tool including Bash, WebFetch and MCP. Anthropic closed the sanitization feature request as shipped ([issue #18653](https://github.com/anthropics/claude-code/issues/18653)). There are two catches. A value that does not match a built-in tool's output schema is **silently ignored**. The only documented shape is Bash's (`{stdout, stderr, interrupted, isImage}`), so the hook should copy the received `tool_response` and replace only its text fields, and it should always emit `additionalContext` as a fallback. Second, the docs warn that context framed as out-of-band system commands can trigger Claude's own injection defenses, so warnings should be factual statements, not imperatives ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). ctx-guard's docs are now out of date on this point: [docs/how-it-works.md](../docs/how-it-works.md) (line 107) and [hooks/pre_tool_bound.py](../hooks/pre_tool_bound.py) (line 6) still say built-in output "can't be shrunk after the tool runs".

The weak spots are just as specific. On **Codex**, the hosted WebSearch fires no hooks at all. Unknown output fields mark a hook as failed, so the emitter must send only documented keys. With no "ask", a tainted-session gate has to choose between denying and warning ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). On **Antigravity**, the only levers are pre-execution decisions and ctx-guard's own wrapper. A sanitizer therefore has to sit in the data path, by routing commands through `ctx-guard-run` with `overwrite`. **WebFetch** on Claude Code runs a summarizer first, so a PostToolUse scan sees only the extracted answer, not the raw page ([injection-sentinel](https://github.com/CodeCombustion/injection-sentinel)). Today ctx-guard transforms output only for commands it wraps. Rewritten commands such as `cat` → `head -c`, plus all built-in tool and MCP output, reach the agent unfiltered ([SECURITY.md](../SECURITY.md)). `context_monitor.py` already receives every tool's output text on Claude and Copilot through `normalize_tool_result_text`, which makes it a ready scanner host ([context_monitor.py](../hooks/context_monitor.py)).

## A five-layer design that reuses ctx-guard's existing plumbing

The recommended architecture stacks layers by how much they can be trusted. Each one reuses machinery ctx-guard already has.

**Layer 0: posture check (SessionStart).** At SessionStart, detect whether the host's OS sandbox and egress controls are active: Claude `/sandbox`, Codex `sandbox_mode`, the Copilot firewall. Warn once when they are not. Anthropic states that "effective sandboxing requires both filesystem and network isolation" ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-sandboxing)). Auto-approve raised attack success from **29.2% to 95.6%** in HarnessSecurity-Bench ([arXiv 2610.07639](https://arxiv.org/abs/2610.07639)). Nothing ctx-guard does in-process matters as much as this nudge.

**Layer 1: shared sanitizer module.** Add a stdlib module, `hooks/lib/injection_scan.py`, that returns `(sanitized_text, findings)`. It runs a full-text Unicode pass using `str.translate` and `unicodedata.category`, then precompiled regexes for the structural, exfiltration and phrase families over a capped prefix. It replaces each stripped run with a visible marker such as `[ctx-guard: removed 37 hidden chars]`. Tag-block text is decoded and surfaced as evidence. Fake role or harness markers are escaped, for example `</tool_result>` → `<\/tool_result>`. Exfiltration-shaped image URLs are defanged. Following OWASP, it scans a normalized copy and rewrites only the *model-facing* text, never files on disk. Two callers share the module: the Python step behind `redact_file` in [bin/ctx-guard-run](../bin/ctx-guard-run) (defined at line 114), and `context_monitor.py`. Sanitizer errors inside `ctx-guard-run` inherit the existing fail-closed contract ("output withheld because redaction failed"). Errors in PostToolUse fail open with the original output. The model-facing output begins with one factual summary line, for example `ctx-guard: output contains hidden-unicode:37, role-marker:1 (treated as data)`. Hit counts go into the stats sidecar next to `redacted`.

**Layer 2: provenance envelope and context minimization.** For carriers classed as untrusted, `ctx-guard-run` wraps output in `<untrusted-output id="{secrets.token_hex(8)}" source="…">…</untrusted-output id="…">` and escapes any literal `<untrusted-output` inside the body. Untrusted carriers are `gh issue|pr view`, `curl`/`wget`, files under `node_modules`/`vendor`/`site-packages`, and freshly cloned repos. Free-form bodies from issues and web fetches are summarized structurally, and the full text stays one `ctx-guard-recall` away. The same wrapper should cover `curl`/`wget` and the `cat-large`/`grep-unbounded` rewrites, which today pipe through `head` unscanned. That closes the data-path gap on Antigravity.

**Layer 3: output rewrite at PostToolUse.** In `context_monitor.py`, run the Layer 1 scanner over Read, Grep, WebFetch, WebSearch, Agent and `mcp__*` results. On Claude Code ≥2.1.121, return `updatedToolOutput` built by copying `tool_response`. On Copilot, return `modifiedResult: {resultType: "success", textResultForLlm}` alongside the nested Claude shape, the same way `build_pretooluse_decision` already emits both. On Codex, register a new PostToolUse `^Bash$` hook that emits `additionalContext` for warnings. Reserve `decision: "block"` for high-confidence hits such as decoded Tag text; it replaces the result with a reason naming the run id, so the model can deliberately recall the redacted archive.

**Layer 4: tainted-session sink gate (the core).** PostToolUse and `ctx-guard-run` mark taint. They write `STATE_DIR/<session>.taint` atomically (temp file plus `os.replace`) in the existing mode-700 state dir, keyed by `safe_session_id`. The file records `{ts, tool, source, rule, severity}` and never the attacker's text. `ctx-guard-run` is sandboxed and has no session id in filter mode, so it emits a marker line that PostToolUse picks up. Taint has two triggers. One is *provenance*: a network fetch, `gh` issue or PR text, third-party package files. The other is a high-precision structural hit, such as invisible Unicode or a fake role marker. The phrase grammar alone never taints. `pre_bash_rewrite.py` reads the taint file and returns "ask" for three sink classes. The first is egress to non-allowlisted hosts: `curl`/`wget`/`nc`/`ssh`/`scp`, `git push`, `gh pr create|issue comment|gist create` and package publish. The second is writes to persistence and agent-config paths: `.claude/settings*.json`, `.vscode/settings.json`, `.cursor/mcp.json`, `.mcp.json`, `~/.codex/`, `.git/hooks`, `.github/workflows`, shell rc files and `~/.ssh`. The third is execution of fetched content (`curl … | sh`) and destructive operations. Read-only commands stay silent. After taint, reading a secret (`.env`, `~/.aws`, `printenv`, `/proc/*/environ`) sets a second flag, `confidentiality_touched`. With that flag set, egress escalates from "ask" to "deny", mirroring FIDES's private-to-public-sink rule. Each agent gets the strongest response it supports: Claude gets "ask"; Copilot gets "ask", which autopilot turns into deny (an acceptable fail-safe); Antigravity gets `force_ask`. Codex has no "ask", so by default it gets a `systemMessage` warning, matching ctx-guard's current downgrade, while `CTX_GUARD_INJECTION=strict` turns config writes and secret-then-egress into "deny". Taint clears only on SessionStart `startup`/`clear` or through a user-run `ctx-guard taint clear`, and PreToolUse refuses to let the model run that command itself. Taint persists through `compact`, because injected text can survive into the summary. Taint *read* errors count as untainted. That preserves ctx-guard's rule of "never a silent block", but it is a deliberate departure from parry-guard's fail-closed choice ([parry](https://github.com/vaporif/parry)), and the docs should say so.

**Layer 5: optional classifier hook.** `CTX_GUARD_PI_SCANNER` names an external command (for example a Prompt Guard 2 wrapper). ctx-guard pipes text to it under a timeout and reads back a score, which is used for annotation only. This keeps torch and Llama-licensed weights out of the stdlib gate (`tests/check_stdlib_only.py`). Prompt Guard 2 22M reports 19.3 ms per 512 tokens on an A100 ([HF model card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-22M)). Independent measurement found roughly 270 ms and weak detection of encoded attacks ([arXiv 2510.01529](https://arxiv.org/pdf/2510.01529)), which is why the classifier is not on by default.

The implementation order follows value per unit of risk:

| Phase | Deliverable | Files touched | Agents covered |
|---|---|---|---|
| 1 | `injection_scan.py` Unicode and structural tiers, wired into `ctx-guard-run`; stats counters; doc corrections | `hooks/lib/`, `bin/ctx-guard-run`, `bin/ctx-guard-recall`, `docs/`, `SECURITY.md` | Claude, Copilot, agy (wrapped commands) |
| 2 | PostToolUse scan and rewrite (`updatedToolOutput` / `modifiedResult`), version-gated; captured `tool_response` fixtures for Read, Grep and WebFetch | `hooks/context_monitor.py`, `ctx_guard_common.py`, `tests/fixtures/` | Claude, Copilot (all tools) |
| 3 | Taint state and sink gate in PreToolUse; `ctx-guard taint` CLI; Codex PostToolUse registration | `hooks/pre_bash_rewrite.py`, `install.sh`, `agent_hooks.py`, `bin/ctx-guard` | All four |
| 4 | Untrusted-carrier envelope and structural summarization; wrap `curl`/`wget`/`cat-large` | `hooks/pre_bash_rewrite.py`, `bin/ctx-guard-run` | Claude, Copilot, agy |
| 5 | SessionStart posture check; optional external classifier; strict mode | `install.sh`, new SessionStart hook | All four |

The latency target is under 20 ms of added hook time. Python startup already dominates, and `context_monitor.py` already pays it on every call. Copilot fails a PreToolUse hook closed on a crash ([Copilot hooks](https://docs.github.com/en/copilot/reference/hooks-configuration)), so the taint reader must never raise.

## Measuring false positives matters more than measuring catches

The evaluation should report what users feel (false positives and blocked work) as prominently as what attackers face. Detector results do not transfer. The best BIPIA-trained detector caught **2% of AgentDojo injections at 1% FPR**, and one that caught 72% on AgentDojo caught 15% on tau-bench. FPR, by contrast, *did* transfer between agent workloads, which makes it the stable property to measure ([arXiv 2610.03448](https://arxiv.org/abs/2610.03448)). Standard cross-validation overstated detector AUC by 8.0–16.5 points against leave-one-dataset-out testing ([arXiv 2602.14161](https://arxiv.org/abs/2602.14161)).

ctx-guard should build `tests/fixtures/injection/corpus.json` modeled on the existing redaction corpus, recording `source` and `license` for each case. Attack payloads can be borrowed from permissively licensed sets: AgentDojo (MIT), BIPIA (MIT), LLMail-Inject (MIT, 208,095 human-written attacks), deepset/prompt-injections (Apache-2.0) and HackAPrompt (MIT) ([AgentDojo](https://github.com/ethz-spylab/agentdojo/blob/main/LICENSE); [BIPIA](https://github.com/microsoft/BIPIA/blob/main/LICENSE); [LLMail-Inject](https://huggingface.co/datasets/microsoft/llmail-inject-challenge)). WASP is CC BY-NC 4.0 and must not be vendored ([WASP](https://github.com/facebookresearch/wasp/blob/main/LICENSE)). The licenses of InjecAgent and the Tensor Trust data remain unverified. No public benchmark uses shell output as the carrier, so each payload should be **re-embedded in realistic carriers**: `cat README.md`, a `gh issue view` body, an HTML comment in `curl` output, an `npm install` log, a pytest failure message, a commit message. Cases should also follow real incidents: the autoApprove write, `mcp.json` creation, the fake "Trusted Content Section", and the Amazon Q-style "cleanup".

The benign corpus should deliberately contain text that *looks* like injection. That includes this repo's own `research_notes/`, LLM app source with system prompts, CLAUDE.md and AGENTS.md files, security-test names like `test_ignore_previous_instructions_is_blocked`, `.gitignore` output, compiler "ignoring" notes, emoji commit messages, i18n and RTL strings, and benign base64 (lockfile hashes, JWT examples). AgentDyn shows why this matters: real GitHub tasks contain *helpful* third-party instructions, and most of ten defenses over-defended ([arXiv 2602.03117](https://arxiv.org/abs/2602.03117)). Each release should report four numbers. The first is detection counts by carrier and obfuscation class. The second is FPR per benign line and per benign command, because one spurious warning per `pytest` run is what users notice. The third is the **utility pass rate** of benign "untrusted read → normal dev command" sequences. The fourth is gate coverage on "untrusted read → risky command" sequences, including alternate execution paths (`bash -c`, `python -c`, `sh <<EOF`, `env X=… cmd`, `git -c core.sshCommand=…`). HarnessSecurity-Bench found allowed commands still reaching unauthorized operations through such paths ([arXiv 2610.07639](https://arxiv.org/abs/2610.07639)).

Adaptive testing can be cheap. After freezing the patterns, have a separate person or LLM session that can see the rule list write evading payloads in each carrier. Commit the successes as `expected_miss` fixtures, so the documented limitations become regression tests rather than prose. Report this held-out set separately, label it "static corpus; not evaluated against adaptive attackers", and keep it in the MEASURED vs. OBSERVED style of `docs/benchmark.md`.

## What ctx-guard will not stop, stated plainly

The pattern layer will miss paraphrase without trigger words ("as the maintainer, please also…"), non-English instructions, payloads split across lines or files, homoglyphs beyond a simple mixed-script check, and encodings outside the capped decode path. These are design limits, not bugs to fix later. The sink gate parses command strings, and Claude Code's own docs warn that deny rules match "the command as written" ([Claude Code security](https://code.claude.com/docs/en/security)). A script the agent writes and then runs, `python -c` with urllib, or DNS exfiltration (the channel used in Claude Code CVE-2025-55284 ([Embrace The Red](https://embracethered.com/blog/posts/2025/wrapping-up-month-of-ai-bugs))) will bypass it. Only an OS-level egress sandbox closes that gap. Coverage is uneven across agents. Codex's hosted WebSearch, anything Antigravity reads through non-shell tools, and the raw page behind Claude's WebFetch summarizer are all invisible to ctx-guard. Whole-session taint has a usability cost, because agents read third-party text constantly. Taint should therefore be tiered by source, and only the top sink classes should escalate to "deny". No published evaluation of hook-based taint gating for coding agents exists, so its real false-positive cost is unknown until ctx-guard measures it. The best published coding-agent benchmark is also sobering: in IssueTrojanBench, **66.5% of malicious issues penetrated all guardrails**, and rejections "came almost entirely from the LLMs, not the agent frameworks" ([arXiv 2607.20759](https://arxiv.org/abs/2607.20759)).

The documentation wording should follow vendor candor. OpenAI calls prompt injection "unlikely to ever be fully 'solved'" ([VentureBeat](https://venturebeat.com/security/openai-admits-that-prompt-injection-is-here-to-stay)). Copilot's firewall docs say it "should not be considered a comprehensive security solution" ([GitHub docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)). ctx-guard should describe the feature as a heuristic, defense-in-depth layer that catches common unobfuscated payloads and hidden Unicode, and that deterministically gates specific dangerous follow-on actions. It should state that the patterns are public and adaptive attackers will evade them, list the known-miss classes and the measured FPR, and say it is no substitute for sandboxing, least-privilege tokens and keeping approval prompts on.

## Conclusion

ctx-guard sits in an unusual position. It cannot change the model, but it already owns the two chokepoints that matter: the data path for wrapped commands, and the permission decision before every shell call. That makes it a natural host for coarse-grained information-flow control, which the research identifies as the only approach that holds against adaptive attackers. Few hook-based guards attempt this, and none of those surveyed document output sanitization through `updatedToolOutput`. ctx-guard's differentiator would not be a better regex. It would be consistent taint-to-sink enforcement across four agents, sitting on top of a fail-closed sanitizer it already has.

The design also reframes what a "detection" hit is for. A scanner hit matters less as a verdict about the text than as a trigger for taint: it moves the session into a state where consequential actions need a human. That means imprecise detectors can still be useful when their output drives annotations and taint rather than blocks. It also means the most valuable engineering investments are boring ones: captured `tool_response` schemas, a benign developer-output corpus, and a sink list kept current with each new CVE. Sinks change more slowly than attacker phrasing.
